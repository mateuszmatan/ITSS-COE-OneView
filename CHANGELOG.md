# Changelog

## [Unreleased]

### Added
- **Liquibase steps of Gradle, Android, Maven and .NET services, and the SonarScanner version of every build tool** (item 2.7 of `TODO.md`). Under Advanced settings, a Gradle, Android, Maven, C# / .NET or MSBuild service has a *Liquibase step after the build* (`build.liquibase`) and a *Liquibase step after the unit tests* (`tests.unitTests.liquibase`), and a Gradle or Maven service a *Liquibase step after the compile* of the SAST scan (`asoc.liquibase`), shown while the compile runs: the `liquibase` command of the agent with its commands, directory, flags, environment variables, label and output switch, as the library runs them, and no Maven home. A step needs commands or flags, because the library skips one without them, and runs `validate` with flags only. Its help says when it runs, that a failure fails the build after the build and makes the build unstable after the unit tests, that the step after the unit tests needs the unit test tasks or goals of a Gradle, Android or Maven service and makes a .NET service run its unit tests, its .NET commands or, while those are empty, the automatic ones, and that the scan runs the step after the build while its own is empty; for any other build tool the form shows no step and the API refuses one. The *SonarScanner version* (`tools.sonar.sonarScannerVersion`) moves from the Flutter section to the Advanced settings of SonarQube, whose summary line names it, and is rendered for every build tool but C# / .NET and MSBuild, whose SonarScanner for .NET does not read it; before, only a Flutter service rendered it. The import reads the steps (the `commands`, else the `tasks`) and notes a step without commands, tasks and flags; such an `asoc.liquibase` of a Gradle or Maven service, also one whose values are all empty, keeps the AppScan compile of the library from running `build.liquibase`, which the portal cannot do, so while `build.liquibase` runs and the compile is on, its note says that the compile runs `build.liquibase` after the import. The import turns `tools.sonar.liquibase` of a Gradle, Android or Maven service into `-Dsonar.` flags of its SonarQube command while it has SonarQube tasks or goals, the only analysis that reads it, imports the SonarScanner version of every build tool but .NET, and notes `delivery.liquibase` with the reason that no stage of the library reads it, for every build tool; before, it noted the steps as not imported. Changeset 051 (`051-service-liquibase-step`, `051-service-liquibase-step-check`, `051-service-sonar-scanner-version` and `051-service-sonar-scanner-version-copy`, one statement each, so that a statement that fails leaves nothing half applied) adds the columns of the steps and copies the version from `FLUTTER_SONAR_SCANNER_VERSION` to `SONAR_SCANNER_VERSION`: every saved service starts without a step, every saved Flutter service keeps its version and renders as before, and a rollback copies the version of every Flutter service back. `FLUTTER_SONAR_SCANNER_VERSION` stays, no longer read or written, so that the pod of the previous release keeps serving during the rolling update; a later release drops it (item 3.9 of `TODO.md`). The API takes the steps as `build.liquibase`, `unitTests.liquibase` and `appScan.liquibaseCompileCommand` and the version as `sonar.sonarScannerVersion`. Every request that worked before keeps working: without the new fields it saves a service without steps, and the `flutter.sonarScannerVersion` of a Flutter service fills `sonar.sonarScannerVersion` while that is empty, so a version in the new place wins; a response of a Flutter service holds the version in both places, so a client of the earlier API, such as a OneView page opened before the upgrade, keeps it when it saves the service. The guide has the new section *A Liquibase step in a Gradle, Android, Maven or .NET service* in chapter 7, the steps and the version in the field reference, the import notes and the upgrade note of changeset 051; the README has the upgrade note and no longer lists the gap.
- **Build tool MSBuild** (item 2.5 of `TODO.md`). *C# / .NET Framework (MSBuild)* is a build tool of its own next to C# / .NET, for a service and in the Library defaults. It renders `buildTool: msbuild` with the keys of C# / .NET, the ".NET commands" under `build.dotnet`, `tests.unitTests.dotnet`, `tools.sonar.dotnet` and `asoc.dotnet` and the NuGet feeds under `delivery.nuget`, and needs no JDK path. The library reads these `dotnet` blocks for `buildTool: msbuild` as well and builds such a service with NuGet.exe and MSBuild.exe, while it keeps choosing the dotnet CLI, MSBuild or both from the projects and the agent for C# / .NET. The hint and the help of the build tool and the help of the .NET commands describe the MSBuild step, and a repository scan that finds .NET code keeps the build tool MSBuild of a service and says so in its result. The help of the .NET command fields of both .NET build tools says for each step what the library runs while the .NET commands are empty, that it runs the automatic unit tests only when the service sets a value under `tests.unitTests`, that the Flags go only to the automatic commands (those of SonarQube to the begin step and to the build of the analysis), that the Step label names only given commands and that Return the output to the pipeline is not used for .NET; the Flags of SonarQube show a begin step option as example. An import of `buildTool: msbuild`, `vs`, `visualstudio` or `netfx` now becomes MSBuild instead of C# / .NET, and `csharp`, `c#`, `.net`, `net`, `dotnet-cli`, `fsharp`, `vbnet`, `cake` and `nuke` become C# / .NET instead of a note, as the library reads them. The import reads the `msbuild` or `dotnet` block of `build`, `tests.unitTests`, `tools.sonar` and `asoc` that the library takes (for `msbuild` the `msbuild` block when it is a map, else the `dotnet` block, for `dotnet` the other way round), renders an `msbuild` block it reads as the `dotnet` block with a note and notes the other block as not imported. Of the `commands`, `tasks` and `goals` of a .NET block, and of the `commands` and `tasks` of a Liquibase block, the import now takes the first one set, as the library runs it, and notes the others; it took `tasks` over `commands` and left out `goals` before. A command block of the service's build tool that is not a map is noted as not imported instead of being dropped without a note. Changeset `050-msbuild-build-tool` adds `MSBUILD` to `CK_DSO_SERVICE_BUILD_TOOL` and `CK_DSO_GLOBAL_BUILD_TOOL`. Saved services and the Library defaults keep their build tool and render as before, so a service imported from `buildTool: msbuild` earlier stays C# / .NET until MSBuild is chosen for it; a rollback stops at the build tool checks while a service or the Library defaults have the build tool `MSBUILD`. The guide describes both .NET build tools in *npm, pip, Android, iOS and .NET services* (was *npm, pip, Android and iOS services*), lists the .NET keys under *Command fields* and every value of `buildTool` in the field reference; the README has the upgrade note. Not verified on a Windows agent.
- **Continuous integration of OneView** (item 1.5 of `TODO.md`). `ci/Jenkinsfile` is the CI build of a multibranch job of the BBH Jenkins, on every push and pull request and every night on `main`: Workspace, Tools (`ci/prepare.sh`: a JDK 21, a folder with `bin/java` and `bin/javac`, the Node.js and npm versions of `engines` in `frontend/package.json`, and `markdown` of `tools/requirements-docs.txt` in `build/ci/venv` with the newest Python 3.11 or later of the agent; without one the pages of the shared user guides are only not rendered again), Build and tests (`ci/build.sh`: `./gradlew build`, then `ci/changed-files.sh`, which fails the build when it changed a committed file) and Shared files (`ci/shared-files.sh` with both branches of the library, UNSTABLE by default through `CI_SHARED_FILES`). The parameters `CI_JAVA_HOME`, `CI_NODE_HOME`, `CI_BROWSER` and `CI_PERFORMANCE_FACTOR` are tried before the tools of the agent and the defaults of the build; a value that does not fit gets a `[CI] [WARN]` line and the next place, a value equal to that of the agent a `[CI] [INFO]` line. The new Gradle task `checkCi`, part of `check`, compiles `ci/Jenkinsfile` and runs the scripts against fakes (`ci/test/ci-scenarios.sh`, Linux and macOS, at most 10 minutes, with its output in `build/ci-check/ci-scenarios.log`); fake Pythons stand in for the Python of the machine, so the check passes without one. `tools/check-shared-files.sh` and `tools/requirements-docs.txt` come from the library and are shared files of the three sources. The README describes the job. Not verified on the BBH Jenkins.
- **Release of the safe artifact** (item 1.4 of `TODO.md`). The Library defaults page has the block *Release of the safe artifact* under Service defaults: the switch `delivery.release.enabled` (ticked by default), the release repository, the Maven server ID and the Gradle credentials ID, written under `defaults.delivery.release` only where they differ from the library defaults. A Maven, Gradle, npm or pip service on virtual machines sets its own under Deployment, *Release of the safe artifact*: Library default, On or Off, the repository and the login of its build tool. The portal and the API refuse a release repository that is the snapshot repository of the upload (the repository of a Gradle upload, the `-Durl` flag of a Maven upload). An npm or pip service uploads its package in the snapshot delivery stage with Maven goals (`delivery.push.maven`), and a .NET service names its NuGet feeds under Deployment, *NuGet packages* (`delivery.nuget`: the feed, its API key, the release feed and its key, the packages), on virtual machines and on OpenShift. A feed is what `dotnet nuget push --source` takes, a feed address, a folder or the name of a source in `NuGet.Config`, so the portal and the API refuse only quotes in it. Only stage 12 of the Full pipeline pushes to the release feed: the Extended pipeline builds no NuGet package and pushes none. The import of a `devsecops_config.yaml` reads `delivery.release`, the `delivery.push.maven` of npm and pip, and `delivery.nuget` or the older `delivery.dotnet` with its names `repositoryUrl` and `apiKeyCredentialsId`; a key the library does not read for the service is left out with a note. Changeset 049 adds `DELIVERY_RELEASE_*` to `DSO_GLOBAL_SETTINGS` and `NEXUS_DELIVERY_RELEASE_*` and `NEXUS_DELIVERY_NUGET_*` to `DSO_SERVICE`; saved settings keep the release switched on without a repository, so stage 12 stays not required until the DevSecOps team enters one. The help of *Disable Nexus Delivery* says that stage 12 then releases nothing but, in the Full pipeline, the NuGet package of a .NET service, and the help of *Build the frontend with Node.js first* says that the Extended pipeline no longer runs the Node.js build, since its release publishes the files of the Security pipeline. The help of the *Nexus delivery goals* of the Service template names the npm and pip services that list their package files.

The cards of the Main Landing Page show the figures of every area for the choice: the pipelines and their latest results, how many applications take part in the QM Metric Tool and have a Grafana dashboard, and how many teams take part and were assessed, with their average level. `GET /api/pipelines` without `departmentId` lists every pipeline, and `GET /api/monitoring/activity` and `GET /api/samm/overview` take `departmentId` and `productId`: the application wins over the business service, an unknown one is answered with 404, and without them every call answers as before.

Only a team that takes part is assessed (the API answers 409 for the others) and counted in the summaries, its assessments kept while it is taken out; the day of an assessment can be any day up to today in UTC+14, so today in any browser is accepted. When someone else saved a team first, the window and the list show their changes, so the change is made again on top of them. REST API `GET /api/agile/model`, `GET /api/agile/applications`, `GET`/`PUT /api/agile/applications/{productId}`, `POST /api/agile/applications/{productId}/assessments`, `GET`/`DELETE /api/agile/assessments/{id}`; changeset 047 adds `AGL_APPLICATION`, `AGL_ASSESSMENT` and `AGL_ASSESSMENT_LEVEL`, and its changeset `047-enabled-flags` the checks that `ENABLED` of `QA_APPLICATION` and `AGL_APPLICATION` is 0 or 1. ### Renamed
- **The portal is ITSS COE OneView.** DevSecOps Management Portal was its working name. The root package is `com.bbh.itss.coe.oneview` (was `com.bbh.itss.dso.portal`), the Gradle group `com.bbh.itss.coe`, the root project `ITSS-COE-OneView`, the application class `OneViewApplication`, the jar `oneview-<version>.jar`, the Spring application, the container image, the OpenShift Deployment, Service, Route, ConfigMap and Secrets `oneview` (`oneview-config`, `oneview-db`, `oneview-influx`, manifests in `deploy/openshift/oneview`), the log file `logs/oneview.log`, the settings prefix `oneview.` (was `dso.`), the local database `~/bbh-itss-coe/oneview/oneview.mv.db` with `ONEVIEW_DATA_DIR` (was `~/bbh-devsecops/dso-portal/dso-portal.mv.db` with `DSO_DATA_DIR`), and the prefix of the Angular components and style variables `ov` (was `dso`). Changeset `046-oneview-name` renames the first entry of the action history.
- **The Jenkins variable is `ONEVIEW_URL`.** DSOEnhanced reads the address of OneView from the global environment variable `ONEVIEW_URL` (was `DSO_PORTAL_URL`; the report upload also read `PORTAL_URL`) and the label of the agents that read OneView from `ONEVIEW_AGENT` (was `DSO_PORTAL_AGENT`). ### Documentation
- **Report upload of a run with a key**: the README and the guide (chapters 1, 8 and 14, and the new troubleshooting entry *The page of a pipeline says "No Pipeline Report Uploaded"*) describe what DSOEnhanced does now. A run that read its settings with the key or keys of its Jenkinsfile posts its report to `POST /api/dso/reports` without a further setting, once for each key, so every pipeline of a shared job shows the report of the run; `DSO_PIPELINE_KEY` or `PIPELINE_KEY` of a job still wins, an upload waits at most 60 seconds and never changes the result of the build. The API of OneView is unchanged; it is called once for each key of a run. A report whose key is not an active key was looked up by its Jenkins job and answered with HTTP 500 when several pipelines share that job; it is now stored with the pipeline only when exactly one pipeline has the job, and without a pipeline otherwise. The new `PipelineReportRegressionSpec` posts reports as the library does: one run with the keys of two pipelines of one job, a key that is not active for a shared job, and for a job of one pipeline.

### Added
- **Build tools npm, pip, Android and iOS**: a service that is only Angular or Node.js, only Python, an Android app or an iOS app is configured in the portal (`NPM`, `PIP`, `ANDROID`, `IOS`, rendered as `buildTool: npm`, `pip`, `android`, `ios`). For npm the Node.js build of the service is its build (`build.node`, written also without the stage 0 switch); for pip and iOS the build is one command line (`build.pip.commands`, `build.ios.commands`); the unit tests of the three are one command line (`tests.unitTests.commands`, `tests.unitTests.dir`) and their SonarScanner takes flags only (`tools.sonar.<tool>.flags`); Android writes the Gradle blocks. The form shows only the fields the library reads, needs no JDK for npm, pip and iOS, and a save with an unused part of a command is refused. *Import config* reads the names of the library (`python`, `poetry`, `pipenv`, `node`, `nodejs`, `yarn`, `pnpm`, `angular`, `react`, `vue`, `xcode`, `swift`, `cocoapods`, `mvn`, `gradlew`, `dart`). The Library defaults offer the four as the build tool of a new service. Changeset `045-npm-pip-android-ios-build-tools` widens the build tool constraints.

### Changed
- **Where a pull request comment goes**: `POST /api/dso/bitbucket/pull-requests/decorate` reads the files the pull request changes (Bitbucket Server `changes`, Bitbucket Cloud `diffstat`) and follows the rule of the library. A finding in a changed file is a comment under its line; the findings of a file the pull request does not change are one pull request comment that names the file and each line; findings without a file are one pull request comment. When the changed files cannot be read, every finding with a line is tried under its line, as before. The remediation of a finding is shown as **Recommended fix**; the library fills it with the fix recommendation it reads from the AppScan API.
- **Scan & Auto-fill follows the detection of the library**: the order is Flutter, iOS, Maven, Gradle (Android with `AndroidManifest.xml`), .NET, Liquibase changelog, Python, npm at the root, SQL and PL/SQL files. `settings.gradle(.kts)` and `gradle/wrapper/gradle-wrapper.properties` are Gradle markers and `gradlew` alone is none; a Python repository gets the build tool pip with its build command, a repository with only `package.json` or `angular.json` the build tool npm, and the test command of both is left to the default of the library.
- **One version of the user guides**: `docs/USER_GUIDE_PORTAL` and `docs/USER_GUIDE_WITHOUT_PORTAL` are merged with the copies of the library and are the same files in the portal and in both library branches; `tools/render-user-guides.sh` renders their pages from the Markdown files.
- **SQL and PL/SQL files without a changelog**: the build tool *SQL / PL/SQL files (no changelog)* (`SQL`, rendered as `buildTool: sql`, imported from `sql`, `plsql`, `pl/sql` or `pl-sql`). Such a service always has database changes: the form shows the section Database changes without the Changelog file and switches the Liquibase commands of Build and Unit tests off, because the library writes the changelog `dso-changelog.xml` and runs Liquibase itself. *Scan & Auto-fill* chooses it for a repository with only SQL and PL/SQL files, fills the Search folder and ticks the automatic build tool setup. An import of `buildTool: sql` with a changelog or Liquibase commands of its own becomes Liquibase (SQL / PL/SQL) with a note, as the library runs it. Migration 044 adds `SQL` to the build tools of a service; the Library defaults refuse it as the build tool of a new service.
- **Gradle and Maven plugins from the BBH Nexus**: the Global Settings section *Service defaults* has the block *Gradle and Maven plugins* with the checkbox *Retry a Gradle or Maven step with these repositories when a plugin is missing* (`pluginRepositories.enabled`, ticked by default), *Gradle plugin repository* (`pluginRepositories.gradle`) and *Maven plugin repository* (`pluginRepositories.maven`), each an http or https address of letters, digits and `. _ / + @ : = , ~ % -` only. The portal renders them under `defaults.pluginRepositories`; an empty repository is left out, so the library uses the one of its own defaults. *Import config* notes the three keys of a service as Global Settings values. Liquibase changeset 043 adds `PLUGIN_REPOSITORIES_ENABLED`, `GRADLE_PLUGIN_REPOSITORY` and `MAVEN_PLUGIN_REPOSITORY` to `DSO_GLOBAL_SETTINGS`, with 1 and the repositories of the BBH Nexus for the saved settings; a `PUT /api/settings` without the fields ticks the box and leaves the repositories empty.
- **Stages at the same time**: the Global Settings block *Speed* has the new checkbox *Run the regression, smoke and performance tests and DAST at the same time* (`dynamicAnalysis.parallel`, ticked by default) next to *Run unit tests, Nexus IQ, SAST and SonarQube at the same time* (`staticAnalysis.parallel`, formerly *Run Nexus IQ and SonarQube while AppScan scans*, ticked by default), and both help texts describe the parallel branches of the library. The portal renders `defaults.dynamicAnalysis.parallel`, and *Import config* notes `dynamicAnalysis.parallel` of a service as a Global Settings value. Liquibase changeset 042 adds `PARALLEL_DYNAMIC_ANALYSIS` to `DSO_GLOBAL_SETTINGS`, 1 for the saved settings; a `PUT /api/settings` without `scans.parallelDynamicAnalysis` ticks it.
- **Nexus delivery upload and download**: a Maven or Gradle service on virtual machines lists the files of its snapshot upload and of the download of the Extended pipeline under Deployment. The portal renders `delivery.push.maven` (with the goals of the upload and its `artifacts`; without artifacts `delivery.maven` and `build.buildPath` as before), `delivery.push.gradle` (`group`, `artifact`, `repositoryUrl`, `allowInsecureProtocol`, `artifacts`, flags and environment variables) and `delivery.pull` (`outputDirectory`, `group`, `artifact` and the `maven` or `gradle` block with its `artifacts`). *Import config* reads them back, keeps one group, artifact and repository for the upload and the download and notes a different second one. Liquibase changeset 041 adds the `NEXUS_DELIVERY_*` columns to `DSO_SERVICE`.

- **C# / .NET services**: the build tool `DOTNET` (rendered as `buildTool: dotnet`, imported from `dotnet` or `msbuild`) with its optional commands under `build.dotnet`, `tests.unitTests.dotnet`, `tools.sonar.dotnet` and `asoc.dotnet`; no JDK and no commands are required, since the library detects the .NET mode on the agent. The repository scan selects it from `*.sln`, `*.csproj`, `*.fsproj`, `*.vbproj`, `global.json`, `Directory.Packages.props`, `Directory.Build.props`, `packages.config` or `build.cake`. - **Auto-resolved settings**: *Scan & Auto-fill* returns `resolvedParameters` (setting, value, why) and the service form lists them under the result. A report upload may carry the library's `autoResolved` list (service, setting, value, why), which is stored with the run (`DSO_PIPELINE_REPORT.AUTO_RESOLVED`) and returned by `GET /api/pipelines/{id}/report`.

### Changed
- **Disable Nexus Delivery** is rendered as `delivery.nexusDeliveryEnabled: false` instead of `deploy.<target>.rd.nexusDeliveryEnabled: false`. The library reads the new key first and the old one without it, so existing configs keep working, and the import reads both, noting an old key that the new one overrides.
- **One AppScan API key for every service**: the AppScan API key ID and the secret credentials ID are gone from the service form, the Self-service wizard, the API (`appScan.keyId`, `appScan.secretCredentialsId`) and the rendered configuration (`asoc.keyId`, `asoc.token`). The library signs in with the API key of the functional user, which the DevSecOps team sets in `asoc.keyId` and `asoc.token` of its `resources/com/bbh/devsecops/defaults.yaml`; a service needs only its AppScan application ID. The import of a `devsecops_config.yaml` notes `asoc.keyId` and `asoc.token` as not imported. Liquibase changeset 040 drops `APPSCAN_KEY_ID` and `APPSCAN_SECRET_CREDENTIALS_ID` from `DSO_SERVICE`.
- **GoldenFix pre-check runs the unit tests**: the help texts of the GoldenFix commands name the new library defaults, which build the fix and run its unit tests (`mvn -B -q test`, `./gradlew test`, `npm test`, `pytest`, `flutter test` or `dart test`, `dotnet test`); classic .NET Framework projects on Windows are still only restored and built.
- **GoldenFix rules are fixed**: the library raises only direct dependencies, only to a patch-level version (`1.2.3` may become `1.2.5`, never `1.3.0` or `2.0.0`), and opens a pull request only after the pre-check build of the upgraded manifests passes. The settings *Only direct dependencies* and *Verify with a build* are removed from the service form, the global settings and the API; `goldenFix.onlyDirectDependencies` and `goldenFix.verify.enabled` are no longer written, and an imported configuration that still carries them is accepted and the keys are ignored. The old `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS` columns stay in the database, unmapped.
- **NuGet in GoldenFix**: `nuget` joins the GoldenFix ecosystems (also in the global defaults), and the pre-check command for NuGet is written as `goldenFix.verify.commands.nuget`. Liquibase changeset 039 adds `GOLDEN_FIX_VERIFY_NUGET` to `DSO_SERVICE` and `DSO_GLOBAL_SETTINGS`.

### Fixed
- **Scan ID uniqueness**: a service without its own Bitbucket repository (it uses the pipeline repository) may share an AppScan application ID or a SonarQube project key with another service, so a copied service with an empty repository is valid.

  - The guide no longer says that the library reads `tests.unitTests.unitTestResult` and `coverage.reportPath` for the utPLSQL tests of a Liquibase service: utPLSQL results and coverage come with the database changes.
