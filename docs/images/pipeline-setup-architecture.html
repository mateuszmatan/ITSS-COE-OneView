1The user gives the basics: business service, product, team, service and the kind of pipeline.
2OneView reads the sources of the repository and detects what they show: build tool, Java version, where the service runs, the Jenkinsfile. The user completes the rest.
3OneView reads the existing Jenkins job and one build and lists what it read: repository, branch, parameters, retention, triggers. Nothing is changed.
4For each call to Bitbucket or Jenkins, OneView fetches the secret of the generic user from OIS with its certificate. The secret is never stored or logged.
5OneView saves the product, the service and the pipeline and issues the pipeline key.
6OneView creates the missing folders and the Pipeline or Multibranch Pipeline job: repository, Jenkinsfile path, the parameters of the old job and the trigger on changes. It never changes or removes an existing job.
7The team commits the Jenkinsfile that OneView shows after the last step.
8Jenkins finds the change (Poll SCM, or the branch scan of a Multibranch job) and starts the build.
9The Jenkinsfile loads the DevSecOps library, which runs the pipeline.
10The library reads its configuration from OneView by the pipeline key and sends the report of the run back.
